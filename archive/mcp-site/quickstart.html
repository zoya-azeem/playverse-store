Quickstart

Two halves: connect an existing server to a client, then write your own. Budget ten minutes for the first and about thirty for the second.

You will need an MCP-capable client (a desktop assistant, a coding CLI or an IDE extension), plus Node.js 18+ or Python 3.10+ depending on which server you run. Exact config paths differ between clients — check your client's own documentation for where its config file lives.

Part 1 — Connect an existing server

  1. Pick a server

    Start with the filesystem server. It is useful immediately, it is easy to reason about, and its blast radius is whatever directory you point it at.

  2. Add it to your client's config

    Most clients use the same JSON shape: a map of server names to a command, its arguments and optional environment variables.

    mcp config — stdio server
    {
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/Users/you/projects"
      ]
    }
  }
}

    On Windows the path looks like C:\\Users\\you\\projects — remember that backslashes must be doubled inside JSON.

  3. Restart the client

    Config is read at startup, not watched. A full restart — not just a new conversation — is what makes the server appear.

  4. Confirm the tools are there

    Look for the tool indicator in your client's UI, or just ask: "What tools do you have available?" You should see the filesystem operations listed. Then try "List the files in my projects directory."

  5. Add a second server

    Servers compose. Two entries means two independent sessions, and the model can chain across them — read a file with one, fetch a URL with the other.

    two servers, one with an environment secret
    {
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/you/projects"]
    },
    "my-api": {
      "command": "python",
      "args": ["-m", "my_server"],
      "env": { "API_TOKEN": "..." }
    }
  }
}

    Keep real secrets out of the config file where you can — read them from your shell environment or a secrets manager inside the server instead.

Part 2 — Build your own server

A first server is smaller than you expect. The SDK handles the protocol; you write the function bodies and the descriptions.

Python

install
pip install "mcp[cli]"
server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("inventory")

@mcp.tool()
def check_stock(sku: str) -> str:
    """Return the current stock level for a product SKU.

    Use this when the user asks whether an item is available,
    how many are left, or which warehouse holds it.
    """
    # Replace with a real lookup against your system.
    levels = {"TS-100": 42, "TS-200": 0}
    if sku not in levels:
        return f"No product found with SKU {sku}."
    count = levels[sku]
    return f"{sku}: {count} units in stock." if count else f"{sku} is out of stock."

@mcp.resource("inventory://catalogue")
def catalogue() -> str:
    """The full product catalogue as CSV."""
    return "sku,name,price\nTS-100,T-shirt,19.00\nTS-200,Hoodie,45.00"

if __name__ == "__main__":
    mcp.run()

TypeScript

install
npm install @modelcontextprotocol/sdk zod
server.ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "inventory", version: "1.0.0" });

server.tool(
  "check_stock",
  "Return the current stock level for a product SKU. Use this when the " +
    "user asks whether an item is available or how many are left.",
  { sku: z.string().describe("Product SKU, e.g. TS-100") },
  async ({ sku }) => {
    const levels: Record<string, number> = { "TS-100": 42, "TS-200": 0 };
    const count = levels[sku];
    const text =
      count === undefined
        ? `No product found with SKU ${sku}.`
        : count > 0
          ? `${sku}: ${count} units in stock.`
          : `${sku} is out of stock.`;
    return { content: [{ type: "text", text }] };
  }
);

await server.connect(new StdioServerTransport());

The description is the API. The model never reads your implementation — only the name, the description and the schema. Say what the tool does, when to reach for it and what it returns. A vague description is the single most common reason a tool goes unused.

Part 3 — Test it without a model

Debugging through a chat interface is slow, because you cannot tell a bad tool description from a broken handler. The Inspector gives you a direct UI onto your server: list the tools, call them with arguments you choose, read the raw JSON back.

run the inspector against your server
npx @modelcontextprotocol/inspector python server.py

Work through this list before you wire the server into a client:

  • Does the server appear as connected, with the protocol version negotiated?
  • Does every tool show up in tools/list with the schema you intended?
  • Does each tool return sensible text for valid input?
  • Does invalid input come back as isError: true with a readable message, rather than a crash?
  • Do your resources list and read correctly?

Troubleshooting

SymptomUsual cause
Server never appears in the client Malformed JSON in the config, or the client was not fully restarted. Validate the file, then quit the app completely rather than reloading the window.
command not found in the logs The client does not inherit your shell's PATH. Use an absolute path to the interpreter — /usr/local/bin/python3, not python.
Connects, then immediately drops Something printed to stdout. Over stdio, stdout carries protocol frames only. Send every log line to stderr instead.
Tools listed but never called A description the model cannot act on. Add when-to-use guidance and concrete argument examples, then test the wording in the Inspector.
Works in the Inspector, fails in the client Environment difference — a missing variable, a relative path resolved against a different working directory, or a permissions gap.
Remote server returns 401 or 403 Token audience mismatch. The server must only accept tokens that were issued for it; passing a token through to a downstream API is the confused-deputy bug.
Large results blow the context window Paginate and summarise inside the tool. Return the 20 rows that matter with a total count, not 10,000 rows of JSON.
