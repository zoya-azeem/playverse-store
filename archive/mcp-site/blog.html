Field notes

Short, self-contained notes on building with MCP — the kind of thing you learn on the third attempt rather than the first. Editorial content written for this site.

14 Nov 2026
Tool design

Your tool descriptions are prompts, so write them like prompts

The model never sees your implementation. It sees a name, a sentence or two, and a JSON Schema — and from that it has to decide whether your tool is the right move right now. search with the description "searches things" will lose every time to search_tickets with "find support tickets by customer email, status or date range; use this before answering any question about a customer's history".

Three habits that pay: name the tool after the domain object it touches, state when to use it rather than only what it does, and put an example value in every schema field description. Then test the rewrite — ask the model the question a user would ask and see whether it reaches for the right thing.

02 Nov 2026
Context

Tool output is a budget, not a dump

The fastest way to ruin an otherwise good server is to return everything. A SELECT * against a wide table can consume more context than the entire conversation that preceded it, and the model then has less room to reason about what it just received.

Decide inside the tool what matters. Return the twenty relevant rows plus a total count. Collapse repeated structure. Offer a fields argument so the caller can ask for more when it genuinely needs more. A tool that returns 400 useful tokens beats one that returns 40,000 tokens containing the same answer.

21 Oct 2026
Security

The confused deputy is the bug to look for

In remote deployments, the recurring serious mistake is a server that accepts any valid-looking bearer token and then uses its own privileged credentials to act on it. That turns your server into a laundering service for authority it was never granted.

The fix is unglamorous: validate that the token's audience is your server, never forward a client token to a downstream API, and derive the user's permissions from the verified identity rather than from anything in the request body. Do this before you add features, not after a review tells you to.

09 Oct 2026
Debugging

Why your stdio server dies on connect

Almost always one cause: something wrote to stdout. A stray print, a library's startup banner, a progress bar from a package manager. Over stdio, stdout carries protocol frames exclusively, so a single stray line corrupts the stream and the client drops the session.

Route every log to stderr, and reach for the protocol's own logging/setLevel once you need levels the host can control. If you inherit a noisy dependency, redirect its handler explicitly at startup rather than hoping it stays quiet.

27 Sep 2026
Architecture

Resources are underused, and it shows

Most servers ship tools only, which pushes every piece of context through a function call the model has to decide to make. Resources invert that: the host attaches them, so schema, configuration and reference material are present from the first turn without the model spending a round trip to ask.

A good rule: if the answer to "would the model want this nearly every time?" is yes, make it a resource. Reserve tools for things that depend on a decision or have a side effect.

15 Sep 2026
Reliability

Two kinds of error, and only one is useful

A JSON-RPC error means the protocol broke — unknown method, malformed params. A tool error is a normal result with isError: true, and that one reaches the model, which can read the message and change course. Conflating them wastes the agent's best recovery mechanism.

So write tool errors for a reader: "No customer found with that email — try search_customers by name" is actionable. "Error 500" is not. The model is the audience for that string, and it will do something sensible if you let it.

03 Sep 2026
Practice

Fewer tools, better named

Thirty tools on one server is a smell. Selection accuracy degrades as the list grows, especially when several names could plausibly match a request, and the model starts picking the first near-miss.

Consolidate variants behind one tool with an enum argument. Split genuinely different domains into separate servers, which a host can enable per workspace. Then measure: run twenty realistic requests and count how often the right tool was chosen first.

22 Aug 2026
Trust

Everything a server returns is untrusted input

A fetched web page, a database row, a ticket comment — any of them can contain text shaped like an instruction. If your host pipes tool output straight back into the model with no framing, you have built a prompt-injection channel with a nice UI on top.

Label tool results as data in the surrounding context, keep destructive operations behind explicit human approval, and never let one tool's output silently authorise another tool's call. Injection is the hard problem in this space and it is not solved by hoping.
