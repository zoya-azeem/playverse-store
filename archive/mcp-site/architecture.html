How MCP is put together

Three participants, one stateful session each, a fixed message vocabulary and two standard transports. This page walks through all of it.

The three participants

The naming trips people up, because "client" does not mean "the app you clicked on". It means the connector inside that app.

HostOwns the model, the UI, and every approval decision
→
ClientOne per server. Negotiates and keeps the session
⇆
ServerExposes primitives, holds the credentials

Host

The application a person uses: a desktop assistant, an IDE extension, an agent you wrote. It holds the conversation, calls the model, and is the only participant that can ask the user for consent.

Client

A connector object inside the host, one instance per connected server. It performs the handshake, tracks that server's capabilities, and isolates it from the others. A host with five servers runs five clients.

Server

A separate program — a local subprocess or a remote HTTP service — that answers protocol messages. It owns its own credentials and should enforce its own access rules. Never trust the caller to do that for you.

Isolation is the point. Because each server gets its own client and its own session, one misbehaving server cannot read another's data or capabilities. Keep that boundary intact when you design a host.

Session lifecycle

  1. Initialise

    The client sends initialize with the protocol version it wants and the capabilities it offers. The server replies with the version it will actually use plus its own capabilities. If the versions are incompatible, the connection ends here.

  2. Confirm

    The client sends the notifications/initialized notification. Only now may either side send ordinary requests. Jumping the gun is a protocol error.

  3. Discover

    The client calls tools/list, resources/list and prompts/list — but only the ones the server declared. Results are paginated with an opaque cursor, so loop until the cursor is absent.

  4. Operate

    Requests flow in both directions for as long as the session lives: tools/call, resources/read, prompts/get from the client; sampling/createMessage or elicitation/create from the server.

  5. Stay in sync

    When a server's offerings change it emits notifications/tools/list_changed (and the equivalents for resources and prompts). The client re-lists. Resource subscribers also get notifications/resources/updated.

  6. Shut down

    No shutdown message exists. Over stdio the client closes the input stream and waits for the process to exit; over HTTP it simply stops issuing requests and lets the session expire.

Message types

Everything is JSON-RPC 2.0, which gives you exactly three shapes. Requests carry an id and expect a reply. Responses echo that id and carry either result or error. Notifications have no id and get no reply.

Request — the client calls a tool
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "query_orders",
    "arguments": { "region": "EMEA", "since": "2026-10-01" }
  }
}
Response — content blocks, never raw JSON strings
{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "content": [
      { "type": "text", "text": "412 orders, 1.84M total value." }
    ],
    "isError": false
  }
}

Two kinds of failure. A protocol failure (unknown method, malformed params) is a JSON-RPC error. A tool failure — the query timed out, the record does not exist — is a normal result with isError: true and an explanatory message. The second kind reaches the model, which can then retry or change course. The first kind does not.

Notification — no id, no reply
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}

Transports

The message layer is identical either way; only the pipe changes. Pick by where the server runs, not by preference.

Local

stdio

The client launches the server as a child process and exchanges newline-delimited JSON over stdin and stdout.

  • No ports, no network, no auth layer to get wrong
  • Inherits the user's own machine permissions
  • Dies with the host, so no orphaned state
  • Never write anything but protocol frames to stdout — logs go to stderr
Remote

Streamable HTTP

The server exposes a single endpoint. The client POSTs requests; the server may reply with one JSON body or an SSE stream for progress and server-initiated messages.

  • One server serves many users
  • Sessions tracked with an Mcp-Session-Id header
  • Authorisation is OAuth 2.1-based for public deployments
  • Supersedes the older HTTP+SSE two-endpoint design

If you deploy over HTTP: validate the Origin header to block DNS-rebinding attacks, bind to 127.0.0.1 rather than 0.0.0.0 when the server is only for local use, and never accept a token that was not issued for your server. Confused-deputy problems are the most common serious bug in remote MCP deployments.

Security boundaries worth drawing

Consent belongs to the host

Only the host can see the user. It must show what a tool will do and get approval before a side-effecting call — not after. Servers cannot be trusted to self-police, and a prompt asking them to is not a control.

Tool results are untrusted input

A fetched page or a database row can contain text engineered to look like an instruction. Treat everything that comes back from a server as data. This is the main prompt-injection surface in any MCP deployment.

Least privilege, enforced server-side

Give a server read-only credentials when reading is all it does. Scope filesystem access to specific directories. Check permissions inside the tool handler, because that is the only place the check cannot be skipped.

Install sources are a supply chain

A stdio server runs with your user's privileges on your machine. Read the code, pin the version, and prefer servers whose source you can inspect over an opaque binary.
