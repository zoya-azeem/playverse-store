The Model Context Protocol (MCP) is an open standard that lets AI applications connect to tools, data and prompts through one consistent interface. Write an integration once, and every MCP-capable client can use it. This site explains how the protocol works and how to build on it.

The problem

Every integration used to be bespoke

A language model is only as useful as the context it can reach. Before MCP, wiring a model to your wiki, your database and your ticket tracker meant writing custom glue for each pairing — and writing it again for the next AI application you adopted.

That is an M×N problem: M applications multiplied by N data sources. MCP turns it into an M+N problem. Each application speaks the protocol once. Each data source implements it once. They interoperate without knowing about one another.

Without a shared protocol

4 apps × 5 data sources = 20 custom integrations to write and maintain.

With MCP

4 clients + 5 servers = 9 pieces, each written once, all composable.

Core concepts

Three things a server can offer

Everything in MCP reduces to a small number of well-defined primitives. Learn these and the rest of the spec falls into place.

⚙

Tools

Functions the model can call to do something: run a query, file an issue, send a deploy. Model-controlled, so the host should keep a human in the loop for anything with side effects.

📄

Resources

Read-only context identified by URI: a file, a table, a page of documentation. Application-controlled — the host decides what gets attached to a given conversation.

💬

Prompts

Reusable, parameterised templates that package expertise — a code-review checklist, an incident postmortem skeleton. User-controlled, usually surfaced as slash commands or menu items.

Clients can offer capabilities back the other way too — sampling, roots and elicitation. See the architecture page.

How it works

Host, client, server

A host application spawns one client per server. Each client keeps a single stateful session over JSON-RPC 2.0.

Host Claude Desktop, an IDE, your own app
→
Client One session per server, manages the connection
⇆
Server Exposes tools, resources and prompts
→
Your system Database, API, filesystem, SaaS
Step 1

Initialise

Client and server exchange protocol versions and declare capabilities. Negotiation happens once, up front.

Step 2

Discover

The client lists what is available — tools/list, resources/list, prompts/list — and hands the model a schema it can reason about.

Step 3

Invoke

The model picks a tool, the host asks the user to approve it, the client sends tools/call, and the result goes back into the context.

In practice

What people build with it

Coding agents that know your repo

An agent reads the actual files, runs the actual test suite and opens a real pull request — instead of guessing at an API from training data that is months out of date.

Analytics without SQL

A warehouse server exposes a read-only query tool plus schema resources. Analysts ask questions in plain language and get answers from live data, not a stale export.

Support that closes the loop

Ticket history as resources, a refund tool behind an approval prompt, and a triage prompt template. The assistant drafts the reply and the human presses send.

Internal knowledge that stays put

Point a server at your own wiki and run it inside your network. The model receives only what it asks for, and your documents never get bulk-uploaded anywhere.
